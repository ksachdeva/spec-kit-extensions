# Project-Local Template Overrides

Use a project override for a one-off template change that belongs to one
project and should not be versioned as a reusable component. A reusable set of
template or command changes is a preset; a change that adds behavior is usually
an extension.

## Location and Resolution

Put override files under:

```text
.specify/templates/overrides/<template-name>.md
```

Use the logical template filename expected by the workflow, such as
`spec-template.md`, `plan-template.md`, `tasks-template.md`,
`checklist-template.md`, or `constitution-template.md`. Keep the same content
format and placeholder conventions as the template being replaced.

Template resolution order is:

1. Project-local override in `.specify/templates/overrides/`.
2. Installed presets, ordered by priority (lower number wins).
3. Installed extension templates, ordered by extension priority.
4. Core template shipped with the CLI.

The first matching replacement is used. Preset composition strategies are not
applied to project override files.

## Authoring Loop

1. Inspect the artifact generated by the current command and identify the
   template responsible for it.
2. Copy the relevant template into the overrides directory, then make the
   smallest edit that expresses the project rule. Preserve required sections,
   placeholders, and downstream structure.
3. Run the command that consumes the template in a test feature/project and
   inspect the generated artifact. Check that the override won over installed
   presets and extension templates.
4. Record the reason for the override in project documentation or a nearby
   README so maintainers understand why it exists.

## Limits

- Project overrides are for templates, not commands, scripts, hooks, or new
  workflow types.
- Commands are materialized into the active agent's directory; editing a
  template does not alter an agent command.
- If several projects need the same override, promote it to a preset and test
  its installation, priority, and removal behavior.
